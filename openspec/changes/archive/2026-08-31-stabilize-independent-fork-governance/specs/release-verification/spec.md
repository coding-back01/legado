## Purpose

本能力用于规定个人 fork 从发布冻结、候选构建、模拟器预检、指定真机非破坏性验证到普通版正式发布和失败回滚的完整证据链，避免未经验证的 APK 被公开。

## ADDED Requirements

### Requirement: 正式发布必须保持冻结直到全部门禁满足
现有 Latest Release MUST 保留并注明稳定化期间暂停新正式版。只有质量、测试、安全、仓库治理和指定真机门禁全部满足后，系统才可发布新的普通正式版；有理由延期的普通依赖和已完成三态记录的 warning 不单独阻止解冻。

#### Scenario: 任一硬门禁未满足
- **WHEN** 质量检查、安全处置、仓库治理或指定真机验证仍有未完成硬门禁
- **THEN** 系统不得发布新的正式版
- **AND** OpenSpec 总变更保持未归档

#### Scenario: 仅剩已记录的非阻断债务
- **WHEN** 剩余事项只有已按规范记录的 `DEFERRED` warning、低危安全项或普通依赖更新
- **THEN** 这些事项本身不阻止发布资格
- **AND** 发布仍须满足其他全部硬门禁

### Requirement: 模拟器必须承担可丢弃数据的完整核心路径
系统 MUST 尽力在干净的最低 API 21 和目标 API 36 模拟器上运行 Debug 预检，并在可用模拟器中覆盖离线本地文本导入、正文断言、翻页进度和返回书架。实际运行发现的回归 MUST 阻止发布；系统镜像或虚拟化不可用 MUST 如实记录，且不得扩大设备兼容声明或替代指定真机。

#### Scenario: 模拟器完整路径通过
- **WHEN** 干净模拟器安装 Debug 包并导入带唯一标记的离线文本夹具
- **THEN** 系统能够断言正文包含标记、翻页后测试进度增加且返回书架后测试书籍存在
- **AND** 测试数据仅存在于可丢弃模拟器沙箱

#### Scenario: 模拟器发现实际回归
- **WHEN** 任一实际运行的核心路径出现崩溃、错误正文、无法翻页或数据断言失败
- **THEN** 正式发布保持冻结

#### Scenario: 某个模拟器环境不可用
- **WHEN** API 21 或 API 36 系统镜像、模拟器或虚拟化能力不可用
- **THEN** 交付记录明确标记该环境未运行及具体原因
- **AND** 不把缺失环境描述为兼容通过
- **AND** 在已尽力准备且其他实际运行未发现回归时，该环境不可用本身不阻止候选或正式发布

### Requirement: 指定真机验证必须保持用户内容边界
系统 MUST 在每次正式发布前实时核对用户指定设备、Android 版本、目标包名、当前版本和签名，并且只允许同签名原位升级、启动、受限日志/截图/UI 层级、可自动读取的数据数量前后对比，以及不会提交数据的导入预览。正式包无法通过公开接口读取的 SharedPreferences 不得被设为不可完成的硬门禁。系统 MUST NOT 卸载、清数据、删除书籍或书源、恢复备份、跨签名覆盖、确认导入、打开已有书翻页或运行会写用户数据的完整测试套件；原始设备证据 MUST NOT 进入 Git。

#### Scenario: 同签名升级并保持关键数据
- **WHEN** 候选普通版与设备现有 `io.legado.app.release` 使用相同签名
- **THEN** 系统通过原位升级安装候选包
- **AND** 升级后包名、版本、签名、首次安装时间以及公开接口可读的书架和书源数量符合预期

#### Scenario: 签名不匹配
- **WHEN** 候选 APK 与设备现有同包名应用的签名不一致
- **THEN** 系统停止安装与发布验证
- **AND** 不执行卸载、清数据或强制覆盖

#### Scenario: 验证导入预览
- **WHEN** 系统使用离线、唯一命名的假书源打开导入预览
- **THEN** 预览显示预期条目后只执行取消
- **AND** 前后书源数据保持一致

#### Scenario: 首次隐私确认阻断自动化
- **WHEN** 真机启动后要求用户接受隐私协议或其他不可代替的授权
- **THEN** 自动验证停止并报告受阻
- **AND** 系统不得替用户自动同意

#### Scenario: 测试路径会改变阅读进度
- **WHEN** 候选真机路径需要打开已有书、翻页或保存阅读位置
- **THEN** 系统不得在用户正式数据空间执行该路径
- **AND** 将该路径放到干净模拟器或独立测试沙箱

#### Scenario: 采集真机证据
- **WHEN** 自动验证需要查询 `ReaderProvider`、logcat、截图或 UI hierarchy
- **THEN** 系统将书架和书源原始响应直接流入计数器且不回显或落盘，并将日志限定在目标 PID 与时间窗
- **AND** 原始 JSON、书名、URL 和路径不得保存；原始日志和界面文件只保存在 Git 忽略且权限受限的本地目录，版本化记录仅包含脱敏数量、状态、摘要和哈希

### Requirement: 候选 APK 必须完成多层完整性与身份核验
发布候选 MUST 核对 GitHub Release API 报告的资产大小和摘要、下载字节、ZIP 完整性、应用包名、版本信息和签名证书。任一层不一致或下载不完整时 MUST 停止安装和发布。

#### Scenario: 候选 APK 全部核验一致
- **WHEN** 远端大小与下载字节一致、摘要匹配、ZIP 完整、包名为 `io.legado.app.release`、版本符合预期且签名证书为受控正式身份
- **THEN** 候选 APK 可以进入指定真机验证

#### Scenario: 任一核验不一致
- **WHEN** 大小、摘要、ZIP、包名、版本或签名任一项不符合预期
- **THEN** 系统停止候选发布
- **AND** 不基于部分文件推断签名或安装结果

### Requirement: 正式 Release 必须先验证后公开
系统 MUST 先锁定全部聚合门禁绿色且无未处置高危/严重告警的 `master` SHA，由仓库所有者手动触发只含一个普通 APK 的候选或草稿 Release。workflow `head_sha`、tag commit 和 Release target MUST 全部等于该锁定 SHA；质量、安全、APK 和指定真机证据全部通过后才可公开并设为 Latest。公开后，应用内更新器 MUST 能识别同一普通 APK，且发布记录 MUST 说明独立签名、包名、对应提交和迁移边界。

#### Scenario: 全部门禁通过
- **WHEN** 普通 APK 的全部静态、自动化、完整性和指定真机验证均通过，且 workflow、tag、Release target 与锁定 SHA 一致
- **THEN** 系统公开该 Release 并将其设为 Latest
- **AND** Release 中只有普通版 APK

#### Scenario: 候选期间 master 漂移
- **WHEN** 候选验证期间远端 `master` 不再等于锁定 SHA，或任一发布对象指向其他提交
- **THEN** 系统停止并废弃本轮公开资格
- **AND** 从新的绿色 `master` 重新锁定并生成候选

#### Scenario: 更新器回验
- **WHEN** 新 Release 已公开
- **THEN** 当前 fork 更新器能够解析完整版本并唯一选择普通 APK
- **AND** 不选择历史或 `releaseA` 资产

### Requirement: 失败必须停止序列并保留审计记录
当前 Pull Request 或发布验证失败时，系统 MUST 停止后续治理序列并保持发布冻结。未合并问题在原 Pull Request 修复；已合并回归使用独立 revert Pull Request。已经公开的资产不得静默替换或删除审计记录；发布后发现 P0、安全、签名或数据问题时 MUST 重新冻结、警示受影响 Release 并发布经过验证的修正版。

#### Scenario: 有序 Pull Request 验证失败
- **WHEN** 当前治理 Pull Request 的必需检查失败
- **THEN** 后续治理 Pull Request 不得继续合并
- **AND** OpenSpec 总变更保持活跃

#### Scenario: 已合并变更出现回归
- **WHEN** 已合并的独立治理 Pull Request 被确认造成回归
- **THEN** 系统使用可审计的独立 revert Pull Request 回退
- **AND** 不通过重写 `master` 历史隐藏回归

#### Scenario: 发布后发现严重问题
- **WHEN** 已公开版本被确认存在 P0、安全、签名或数据完整性问题
- **THEN** 系统立即恢复发布冻结并在 Release 中给出警示
- **AND** 保留原记录并通过新的验证版本修复

### Requirement: 总变更只能在发布闭环后归档
系统 MUST 在普通正式版公开、更新器回验完成、所有任务证据记录且 OpenSpec 严格验证通过后归档总变更；归档分支和归档合并后的 `master` MUST 分别再次通过全量严格校验，随后按已合并 PR 记录的精确 head ref/SHA 清理临时分支，不得使用 glob，并核对 `master` 与工作区状态。

#### Scenario: 发布完成但尚未归档
- **WHEN** 新普通正式版已经通过验证并公开
- **THEN** 系统完成更新器回验和 OpenSpec 验证
- **AND** 通过最终归档 Pull Request 保存总变更记录

#### Scenario: 任一完成条件缺失
- **WHEN** 发布、回验、任务证据、严格验证或分支清理任一条件尚未完成
- **THEN** 系统不得宣称一次性治理已经完成
